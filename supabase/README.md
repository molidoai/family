# زیرساخت ورود اعضای هم‌سهم — آماده، هنوز متصل یا منتشر نشده

این پوشه شامل migration واقعی PostgreSQL و آزمون کنترل دسترسی است. روی Supabase کاربر اعمال نشده، پنل آنلاین و اتصال به APK هنوز ساخته/فعال نشده و داده صندوق‌های فعلی فقط روی دستگاه مدیر است. APK فعلی همان ۲.۳.۰ است؛ این تغییر به آپدیت APK نیاز ندارد چون هنوز وارد برنامه نشده است.

## دسترسی تعریف‌شده
- کاربر احراز هویت‌شده درخواست عضویت می‌دهد؛ درخواست تکراری وضعیت قبلی را بازنشانی نمی‌کند.
- عضو منتظر/ردشده/معلق فقط وضعیت و مشخصات عضویت خود را می‌بیند.
- مدیر مالک صندوق، درخواست را با شناسه همان عضو در دفتر محلی تطبیق و تأیید می‌کند.
- عضو تأییدشده پیش از اولین تراکنش معتبر، نام و لینک پرداخت صندوق را می‌بیند؛ گزارش‌ها بسته‌اند.
- فقط مدیر می‌تواند واریز سهم یا بازپرداخت واقعی همان عضو را با مرجع یکتا تأیید کند؛ رسید ادعایی عضو دسترسی ایجاد نمی‌کند.
- بعد از وجود حداقل یک تأیید غیرابطال‌شده، خلاصه عمومی صندوق و حساب خود عضو قابل خواندن است؛ حساب و تراکنش دیگر اعضا بسته می‌ماند.
- تعلیق یا ابطال آخرین تأیید معتبر، دسترسی به گزارش‌ها را فوراً در پرس‌وجوهای بعدی می‌بندد. داده‌ای که عضو قبلاً دیده یا ذخیره کرده از دستگاه او پس گرفته نمی‌شود.
- تصمیم‌های عضویت، تأیید و ابطال در سابقه فقط‌خواندنی مدیر ثبت می‌شوند. تغییر مالکیت، تأیید خودسرانه و حذف مستقیم سابقه برای کلاینت مجاز نیست.
- پس از وجود سابقه تأیید، اتصال عضویت به عضو محلی دیگری ممنوع است؛ برای اصلاح هویت به فرایند بازبینی مدیر نیاز است.

## قرارداد سرور برای مرحله اتصال
همه RPCهای زیر با نشست احراز هویت Supabase اجرا می‌شوند. شناسه کاربر از `auth.uid()` گرفته می‌شود و از ورودی برنامه پذیرفته نمی‌شود.

| RPC | کاربرد |
|---|---|
| `hamsahm_create_fund(fund_name,payment_url)` | ایجاد صندوق آنلاین به مالکیت کاربر جاری؛ شناسه UUID برمی‌گرداند |
| `hamsahm_request_membership(fid,member_name)` | درخواست عضویت در صندوق مشخص؛ شناسه عضویت برمی‌گرداند |
| `hamsahm_decide_membership(mid,new_status,member_key,reason)` | مدیر: تأیید، رد یا تعلیق؛ `member_key` شناسه عضو دفتر محلی است |
| `hamsahm_confirm_payment(mid,source_ref,payment_kind,payment_amount,paid_on)` | مدیر: تأیید واریز سهم یا بازپرداخت؛ مرجع تراکنش در هر صندوق یکتاست |
| `hamsahm_revoke_payment(cid,reason)` | مدیر: ابطال تأیید با حفظ سابقه |
| `hamsahm_my_access(fid)` | وضعیت عضویت، مجوز نمایش و در صورت تأیید، نام و لینک پرداخت |

جدول `hamsahm_fund_summaries` فقط عددهای تجمیعی صندوق دارد؛ شماره تماس، نام دیگر اعضا، شماره پیگیری و شرح خصوصی در آن ذخیره نمی‌شوند. `hamsahm_account_summaries` خلاصه حساب شخص عضو است. فقط مدیر می‌تواند این خلاصه‌ها را درج/به‌روز کند و معادله موجودی در پایگاه داده کنترل می‌شود.

تأیید پرداخت در این مدل **فقط مجوز نمایش** را تغییر می‌دهد؛ تراکنش مالی جدید یا وصول بانکی ایجاد نمی‌کند. انتقال دفتر محلی باید جداگانه با تطبیق شناسه‌ها، نمایش پیش‌نمایش، کنترل جمع‌ها و پشتیبان انجام شود. برنامه انتشار آتی باید تأییدهای ابطال‌شده را هم با دفتر مدیر همگام کند تا دسترسی قدیمی باز نماند. همگام‌سازی، آپلود دفتر و تأیید خودکار بانک در این مرحله وجود ندارد.

## اجرای آزمون
از ریشه مخزن:

```sh
npm --prefix supabase ci --ignore-scripts && npm --prefix supabase test
```

آزمون migration را روی PostgreSQL تعبیه‌شده PGlite اجرا می‌کند، نقش‌های `anon` و `authenticated` را عوض می‌کند و ۴۴ حالت مجاز/غیرمجاز را بررسی می‌کند. جدول `auth.users` و تابع `auth.uid()` فقط در محیط تست شبیه‌سازی شده‌اند؛ احراز هویت واقعی، PostgREST، ارسال ایمیل، گوشی و شبکه در این آزمون پوشش داده نشده‌اند. هیچ سرویس یا حساب واقعی برای تست لازم نیست. Workflow `member-access.yml` همین آزمون را روی GitHub اجرا می‌کند و چیزی روی Supabase مستقر نمی‌کند.

## شرط فعال‌سازی واقعی
۱. اتصال حساب Supabase و انتخاب پروژه مستقل هم‌سهم؛ هنوز انجام نشده است.
۲. بررسی پروژه و اجرای migration با نقش مدیریتی، فعال‌سازی احراز هویت و تأیید ایمیل. ارسال پیامک به سرویس جدا نیاز دارد؛ فعلاً قرارداد بر اساس حساب Supabase Auth است.
۳. ساخت پنل ورود و وضعیت عضو، پنل تصمیم مدیر و اتصال برنامه به آدرس همان پروژه با کلید publishable؛ هیچ کلید service-role یا رمز پایگاه داده داخل APK، GitHub یا پیام قرار نگیرد.
۴. تطبیق و انتقال کنترل‌شده داده صندوق مدیر، انتشار خلاصه‌ها و آزمون با دو حساب واقعی مستقل و یک حساب بیگانه؛ سپس انتشار APK جدید.

این پوشه قرار نیست روی پروژه ناشناخته یا حاوی داده موجود خودکار اجرا شود. ابزار اتصال هنگام فراهم‌شدن حساب ابتدا پروژه و migrationهای موجود را بررسی می‌کند. هیچ فایل موجود یا داده‌ای در migration حذف نمی‌شود.
